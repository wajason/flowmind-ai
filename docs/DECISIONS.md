# 決策記錄（Architecture Decision Records）

> **這份文件存在的理由**
>
> 一個專案真正的資產不是程式碼 —— 程式碼會被重寫。
> 真正的資產是「**當初為什麼那樣決定**」，因為那決定了下次遇到類似情況時，
> 你會不會再犯同一個錯。
>
> 每一則記錄都必須回答四件事：
> **當時的處境是什麼 · 做了什麼決定 · 為什麼 · 重來一次還會這樣嗎**
>
> 最後一項最重要。它強迫我們在事後誠實檢視，而不是把每個決定都合理化。

## D-01 用確定性的外殼包住機率性的核心

**日期**：2026-08-07　**狀態**：✅ 維持

### 處境
LLM 輸出本質不可預測。金融場域（授信）對錯誤的容忍度極低。
兩者直接衝突：不能因為「模型通常是對的」就把授信判斷交給它。

### 決定
把系統拆成兩層：**確定性外殼**（可重算、可稽核）與**機率性核心**（可替換的零件）。
13 個核心模組中只有 `llm.py` 呼叫 LLM。
`crosscheck.py` / `metrics.py` / `tables.py` 強制維持零 LLM。

### 理由
凡是有明確規則可以算的 —— 統編檢核碼、稅額、金額加總、集中度、帳齡 ——
交給語言模型只會引入不必要的不確定性。
這些事在 0.1 毫秒內可以用純算術確定，而且**任何人都能用同一套規則重算得到同一個答案**。
「可重算」正是金融場域對一份報告的最低要求。

### 考慮過但否決
- **全部交給 LLM + 好的 prompt**：否決。prompt 再好也無法保證輸出一致，
  同一份發票跑兩次得到不同統編，在會被稽核的場域不可接受。
- **用 LLM 判斷 + 程式複核**：否決。等於做兩次，而且複核發現不一致時還是要人介入。

### 代價
- 決定性層只能處理「規則明確」的問題，規則之外的仍需 LLM
- 每接一個新場域就要新增規則，不會自動泛化

### 重來一次還會這樣嗎？
**會，而且會更早開始。** 這個決定是整個產品的差異化來源，
也是後面所有評測指標能成立的前提。

## D-02 刻意用弱模型開發

**日期**：2026-08-07　**狀態**：✅ 維持

### 處境
開發機是 RTX 4060 Laptop（8GB VRAM）。可以選擇接雲端強模型開發，
或用本地跑得動的小模型。

### 決定
用本地小模型（`qwen3.5:9b`）開發，不接雲端強模型。

### 理由
兩個層面：

**(a) 工程層面** —— 強模型會**遮蔽**系統問題。它靠自身能力補上 prompt 沒講清楚的地方、
自動修正格式漏洞、猜對沒定義的邊界。系統看起來能跑，但你不知道是 harness 好，
還是模型在幫你收拾。弱模型會**暴露**這些問題，每次失敗都精確定位到一個工程缺口。

實際驗證（都是真的發生的）：

| 弱模型暴露的問題 | 用強模型會怎樣 |
|---|---|
| 吐 `<think>` 破壞 JSON | 永遠不會加上 grammar-constrained decoding |
| 用刪節號縮短引用導致驗證失敗 | 驗證器帶著 bug 上線 |
| 檔名多打一個空格 | 強模型不犯，但**生產環境的量化/降級模型會** |
| 24 chunk 灌爆 context 被靜默截斷 | 直到客戶文件變多才爆 |

**(b) 場域層面** —— 銀行不會讓客戶發票流出去給雲端 API。
能離線跑的模型就是比較弱。**架構必須在弱模型上就成立。**

### 考慮過但否決
- **用強模型開發、上線再換小模型**：否決。等於把所有 harness 缺陷留到上線後才發現。

### 代價
- 開發速度較慢（每次推論 30–60 秒）
- 某些能力（長文推理、複雜合成）在小模型上做不好，導致 skill_builder 品質不佳（見 D-19）

### 重來一次還會這樣嗎？
**會。** 但會**同時**準備一組強模型的對照組，用來區分
「這是 harness 的問題」還是「這是模型能力的天花板」。
這次沒做對照，導致 skill_builder 品質差時，花了時間才確認是任務設計問題而非模型問題。

## D-03 中文稀疏檢索用字元 bigram 而非 jieba

**日期**：2026-08-07　**狀態**：⚠️ 待實測驗證

### 處境
PostgreSQL 沒有內建中文分詞。原本沿用的程式碼寫 `to_tsvector('english', 中文)`，
english parser 找不到詞界，會把整段中文吐成極少數超長 token，
導致 BM25 那一路幾乎永遠 0 命中 —— 而 RRF 分數照算、面板照亮綠燈。

### 決定
用**字元 bigram**（「應收帳款」→ 應收/收帳/帳款），
再用 `to_tsvector('simple', bigram字串)` 建 GIN 索引。

### 理由
- Lucene 的 CJKAnalyzer 就是這樣做的，是資訊檢索對 CJK 的標準做法之一
- 無字典、無外部相依，維持「`docker compose up` 就能跑」的可重現性
- 對未登錄詞（公司名、產品型號）比詞典分詞更強韌 ——
  而金融場域大量是專有名詞

### 考慮過但否決
- **`pg_jieba` / `zhparser`**：需編譯 C 擴充，Windows 上很痛苦，且中斷可重現性。
  ⚠️ **後來發現這個否決理由有一半是錯的**：`jieba` 是純 Python，
  可以在 Python 端分詞後照樣用 `to_tsvector('simple', …)`，**根本不需要 PostgreSQL 擴充**。

### 代價
- bigram 會產生跨詞界的垃圾 token（「款承」），增加索引大小與雜訊

### 重來一次還會這樣嗎？
**不確定 —— 這是目前最該補實測的一項。**
應該建 A/B harness 比較三組（dense-only / bm25-only / hybrid）× 兩種分詞（bigram / jieba），
用檢索指標決定，而不是靠推理。
判準已經想好：**如果 hybrid 的指標不比純 BM25 好，hybrid 就是壞的。**

## D-04 隔離下沉到資料庫層（RLS）而非 SQL 加 WHERE

**日期**：2026-08-07　**狀態**：✅ 維持

### 處境
一家財顧公司／銀行企金部門同時服務數十家客戶，法遵上必須有資訊隔離牆。

### 決定
用 PostgreSQL Row-Level Security + `FORCE ROW LEVEL SECURITY`，
應用程式角色刻意**不是** superuser 也**不是** table owner（兩者都會繞過 RLS）。
連線建立時 `SET app.tenant_id`，之後所有查詢由資料庫強制過濾。

### 理由
在 SQL 手寫 `WHERE tenant_id = ?` 是**開發者自律**。
一次 code review 疏漏、一個忘記帶條件的 JOIN，就是跨客戶資料外洩。
**內控稽核不會接受「我們的程式碼有加 WHERE」這種說法** ——
那不是技術控制點，是流程承諾。

RLS 是可稽核的技術控制點：即使程式寫錯、甚至被 SQL injection 打穿，
資料庫層仍然只回傳該 engagement 看得到的列。

### 考慮過但否決
- **每個 tenant 一個 schema/資料庫**：否決。管理成本高，跨 tenant 的共用知識庫（SHARED）
  會變成同步問題。
- **應用層過濾**：否決，理由如上。

### 代價
- HNSW 向量索引先取 ef_search 個候選、再套 RLS 過濾，可能降低召回率
  （已用 pgvector 0.8 的 iterative scan 緩解）
- 連線必須攜帶 tenant 上下文，增加一層呼叫約定

### 重來一次還會這樣嗎？
**會，毫不猶豫。** 而且 `verify_isolation()` 這種「可執行的證明」應該更早寫 ——
它把「我們有做隔離」從一句話變成一個可以當場跑的驗收項目。

## D-05 Embedding 走 Ollama 而非 sentence-transformers

**日期**：2026-08-07　**狀態**：✅ 維持

### 處境
8GB VRAM。sentence-transformers 載入 bge-m3（FP16）固定佔約 2.4GB，
再載入 6.6GB 的 LLM 就會超過顯存。
Ollama 遇到顯存不足**不報錯**，只靜默退回部分 CPU 推論 —— 突然慢 5~8 倍且不知原因。

### 決定
Embedding 也交給 Ollama（同一個 bge-m3），讓它統一管理顯存排程。

### 理由
把「顯存超賣」變成 Ollama 的問題而不是我們的問題。
副作用是這個專案**完全不需要安裝 PyTorch**（省 2.5GB 安裝與大量相依衝突）。

### 代價
- 多一次 HTTP 往返（已用 batch 緩解）
- 綁定 Ollama 的 embedding 實作細節

### 重來一次還會這樣嗎？
**會。** 但會更早發現 —— 這個問題花了不少時間才從「為什麼突然變慢」追到顯存競爭。
教訓：**任何「靜默降級」的行為都應該在系統裡有一個明確的偵測點。**

## D-06 保留 LiteLLM 但長 context 走原生 API

**日期**：2026-08-07　**狀態**：✅ 維持

### 決定
一般問答走 LiteLLM（可換供應商），需要設 `num_ctx` 的長 context 合成走 Ollama 原生 API。

### 理由
LiteLLM 的價值是「換模型供應商只需改 .env 三行」—— 對要進企業 POC 的產品，
被單一供應商綁死是實質風險。

但 LiteLLM 走 OpenAI 相容端點，**無法傳遞 Ollama 的 `num_ctx`**。
Ollama 會套用預設 context，超過的部分**從 prompt 前面直接截掉且不報錯**。
skill_builder 一次灌 24 chunk（約 6 萬字元），六個任務全部回傳空內容，
產出的檔案每一節都是「本節未產生內容」—— API 回 200，沒有任何錯誤訊息。

### 代價
兩條路徑增加複雜度，且原生路徑不可攜。

### 重來一次還會這樣嗎？
**會。** 但會在 `chat_local()` 一開始就加上「回傳空內容時報出 prompt_eval token 數」
的診斷 —— 這個診斷是事後補的，如果一開始就有，那次除錯會快很多。

## D-07 引用驗證用純字串比對，且要求片段順序

**日期**：2026-08-07　**狀態**：✅ 維持

### 處境
業界慣例是請 LLM 在句尾寫 `[來源: xxx.pdf]`。
但那串標籤本身也是模型生成的 token —— 模型可以在完全沒讀那份文件的情況下寫出完美引用。

### 決定
強制模型輸出「逐字摘錄」，程式回到實際檢索到的文本做**字串比對**。
引用允許用刪節號省略，但**拆成片段後要求每段逐字命中且順序與原文一致**。

### 理由
這條路徑上沒有任何一步經過語言模型，所以不可能被「講得更有說服力」騙過。
順序約束是必要的 —— 少了它，模型可以從文件各處挑零碎詞句拼成原文從未表達過的話，
而每個片段都「驗證通過」。

### 考慮過但否決
- **模糊比對（fuzzy match）**：否決。模糊比對的門檻是評測者自己選的，
  等於把「多寬鬆算對」的權力交回給被評的人。（保留 NEAR 判定但**獨立報告**，不混入主指標。）
- **要求模型回報字元位置**：否決。要 LLM 準確數出「第 1,847 個字元」不切實際，
  測到的是它會不會數數，不是它有沒有讀文件。

### 代價
- 對「合成型」任務不友善：模型做跨文件整合時本來就會改寫，
  導致 skill_builder 引用率只有 31.8%（見 D-19）

### 重來一次還會這樣嗎？
**會。** 這是產品最核心的主張。
但會更早區分「抽取型任務」與「合成型任務」—— 兩者對引用的要求本來就不同。

## D-08 HPES 用 proper scoring rule 而非準確率

**日期**：2026-08-07　**狀態**：✅ 維持

### 處境
傳統欄位準確率有個致命弱點：**猜永遠不虧**。猜中加分，猜錯跟留白一樣都是不加分，
理性最佳策略是全部都猜 —— 這正是最不想要的行為。

### 決定
答對 `+1`、留白 `0`、答錯 `−λ`（λ=2）。

### 理由
不可 gameable 是可以算出來的：
```
猜的期望分數 = p·1 + (1−p)·(−λ)；留白 = 0；相等時 p = λ/(1+λ) = 0.667
```
除非真實把握超過 2/3，否則猜的期望分數低於留白。
這不是靠規則禁止亂猜，而是**讓亂猜在數學上不划算**。

λ=2 的依據是真實成本比：編造的統編 → 整份申請退件；空欄位 → 只是補件。

### 實際價值
它讓我們**選對了模型**：`gemma4:e4b` 傳統準確率 66.7% 較高，
但 HPES 只有 +0.042（48 欄位只留白 1 次，猜錯 15 次）；
`qwen3.5:9b` 準確率 62.5%，HPES +0.125（留白 6 次，猜錯 12 次）。
**只看準確率會選錯模型。**

### 重來一次還會這樣嗎？
**會。** 這是本專案最有價值的方法論貢獻之一。
λ 應該公開為可調參數（已做），讓不同成本結構的機構帶入自己的值。

## D-09 四項評測指標不合成單一總分

**日期**：2026-08-07　**狀態**：✅ 維持

### 決定
HPES / CVR / CRC / AURC 分開報告，不加權合成。

### 理由

### 代價

### 重來一次還會這樣嗎？
**會。** 換來的是每個數字都指向一個可獨立查核的能力，這在面對專業評審時更站得住。

## D-10 決定性路由：可以用算的就不給 LLM

**日期**：2026-08-07　**狀態**：✅ 維持

### 處境
實測時問「本案最大買方占營收多少？」，檢索取回 90 張發票中的 3 張，
模型據此寫出四句專業結論，**四句全部沒通過驗證**，信心 0.31，系統拒答。

拒答是對的，但問題在架構：這題需要跨 90 張發票加總，
**RAG 在設計上就不可能可靠地回答彙總問題**。

### 決定
用**關鍵詞規則**（非 LLM 分類器）判斷該走哪條路：
可以用算的走純 Python（信心 1.00、零幻覺、瞬時），需要理解文義才給 RAG。

### 理由
路由用規則而非模型，是為了**可預測性**：使用者問同一句話永遠走同一條路徑。
一個時好時壞的路由，比沒有路由更難除錯。

### 代價與已知風險
規則會誤觸發。實際發生過：統計表列標籤含「2015」，
「依 2015 年版作業手冊…」被判定為統計查詢，回了無關數字**並給信心 1.00**，
完全繞過拒答閘門。已修（標籤須有 2 個以上中文字、排除純數字與通用詞）並加回歸測試。

### 重來一次還會這樣嗎？
**會。** 但會更早意識到：**決定性路徑給滿分信心，等於它繞過了所有安全閘門**，
所以路由的誤觸發成本比想像中高，一開始就該把標籤品質的門檻設嚴。

## D-14 ~~用 RRF 當檢索強度~~ 【已推翻】

**日期**：2026-08-08　**狀態**：❌ **已推翻**

### 原本的決定
信心分數的「檢索強度」分項用 `top_rrf / MAX_RRF`。

### 為什麼是錯的
**RRF 是為了「融合兩份排名」設計的，它只看名次不看相似度** ——
排第一名永遠得 `1/(60+1)`，不管那筆結果到底有多相關。
把它當「絕對相關度」用是概念上的誤用。

實測（各 4 題）：

| | top_dense | rrf/MAX |
|---|---|---|
| 有答案 | 0.691~0.799 | 0.969~**1.000** |
| 知識庫沒有 | 0.581~0.653 | 0.739~**1.000** |

RRF 完全分不出來（無解題也拿 1.000）。

### 後果
問「信保基金的內部評分卡權重為何」（公開文件必然沒有）拿到信心 **0.852** ——
模型從相關但不對題的段落引用了真實存在的句子，引用驗證通過，
檢索強度又被 RRF 灌成滿分。**可驗證 ≠ 切題。**

### 教訓
**用一個工具之前，先確認它衡量的是什麼。**
RRF 是排名融合演算法，不是相關度量表。這個錯誤很基本，但它的後果是安全閘門被繞過。

## D-15 ~~用 8 題探測樣本訂門檻~~ 【已推翻】

**日期**：2026-08-08　**狀態**：❌ **已推翻**

## D-16 範圍詞驗證取代相似度門檻

**日期**：2026-08-08　**狀態**：⚠️ 部分有效

### 處境
D-15 證明 dense 相似度分不開「可答」與「無解」。
反例：「日本的中小企業信用保證協會保證成數是多少」拿 0.7409，比大多數可答問題還高 ——
因為它跟台灣的保證成數在語意空間裡幾乎重合。**embedding 分不出指涉對象是誰。**

同一根因也解釋了另外三題失敗：2027 年的成數、作業手冊第 87 條、2026 年 12 月的統計 ——
全是**主題對、指涉對象不存在**。

### 決定
抽出問題裡的**境外地名／年份／條次**，用字串比對檢查是否出現在檢索文本中。
沒出現 → 答案確定不在這批文本裡，不管相似度多高。

### 理由
這三類範圍詞有兩個共同性質：
(a) 可以用字串比對確認，不需要語意判斷
(b) 一旦問題指定了它而文本沒有，答案就確定不在這批文本裡

### 實測結果（獨立校準集）
| 指標 | 結果 |
|---|---|
| 無解題正確攔截 | **3 / 8** |
| 可答題誤攔 | **0 / 12** |

**精確但不完整。** 誠實記錄，不調整到好看。
「日本」沒攔到是因為白皮書真的提過日本 —— **詞出現 ≠ 該範圍的答案存在**。

### 已知限制與下一步
這個機制是「必要條件檢查」不是「充分條件檢查」。
真正的解法需要**結構化的指涉對象比對**（見 §未來方向），
例如知識圖譜上的實體節點（國家=台灣、年份=2025、法規=供應商融資要點），
把「這份文件在講哪個對象」變成可查詢的結構，而不是靠文字出現與否。

## D-17 計分順序：驗證 → 移除幻覺 → 計分

**日期**：2026-08-08　**狀態**：⚠️ 待重跑驗證

### 處境
50 題完整重跑：拒答紀律 44.4% → 88.9%（大幅改善），
但整體通過率 68% → 58%，**過度保守從 6 題暴增到 16 題**。

### 根因
16 題中有 12 題撞到幻覺上限。追下去發現執行順序是錯的：
```
原本：驗證 → 計分 → 移除幻覺 → 閘門
```
**信心分數描述的是「含幻覺的版本」，但實際輸出的是「已移除幻覺的版本」——用 A 的分數否決 B。**

例如「供應商融資可以憑哪些文件申請撥貸？」答案本身完全正確，
只因夾帶一句無法驗證的敘述（而那句話已被移除），整個答案被拒絕。這是雙重懲罰。

### 決定
改為 `驗證 → 移除幻覺 → 對實際會輸出的內容計分 → 閘門`。
「曾經掰過」仍要罰，但改為扣分（×0.8）而非直接判死。

### 為什麼這不是「把門檻調鬆」
全部主張都無法驗證時，移除後就沒有任何有根據的主張，
`citation_integrity` 為 0，一樣會被拒答。改的是**計分對象**，不是門檻。

### 狀態
⚠️ **尚未重跑驗證。** 不在未量測前宣稱改善。下一輪第一件事就是重跑 50 題。

### 教訓
**看到指標退步時，先問「為什麼」再決定改什麼。**
如果當時直接把門檻調鬆，數字會變好看，但這個順序錯誤會被永久掩埋。

## D-18 Zero-Trust 第一層用確定性規則而非小模型

**日期**：2026-08-08　**狀態**：✅ 維持

### 決定
意圖偵測第一層一律用正則／關鍵詞／頻率統計，不用小模型當警衛。

### 理由
- 用模型防模型是**遞迴的** —— 警衛模型本身也可以被 prompt injection 繞過
- 模型判斷**不可重現** —— 同一句話今天擋明天不擋，稽核時無法交代

### 另外三個設計決定
1. **閘門放在檢索之前**：若先檢索再擋，攻擊者仍可從回應時間差推測資料是否存在
2. **去識別化不對授權使用者做**：對承辦人遮蔽統編只會讓他改用別的方式取得，
   反而把資料帶到系統外。正確用途是稽核紀錄與跨案彙總
3. **遮蔽保留前 3 碼**：稽核人員需要辨識「這幾筆是不是同一家」；
   全遮成 `********` 會讓稽核紀錄失去可用性，那種日誌沒有人會看

### 重要的反向測試
回歸測試中有 4 項是「**正常業務問題必須放行**」——
一個把正常使用者也擋住的安全機制，很快就會被關掉，等於沒有。

### 重來一次還會這樣嗎？
**會。** 但會更早釐清一件事：**零信任不是「拒絕回答機密」，
而是「確保只有有權限的人問得到」。** 這個區分沒講清楚時，
很容易做出一個什麼都不敢答、因而毫無價值的系統。

## D-20 檢索排序補決勝鍵，讓結果可重現

**日期**：2026-08-12　**狀態**：✅ 維持

### 處境
做 A/B 比較時發現：**同一個 query 連跑四次，召回的 chunk 組合有四種。**

### 決定
在三個 `ORDER BY` 全部補上 `id` 當最終決勝鍵，讓排序成為**全序**。

### 理由
逐步歸因，每一步都實測不是猜的：

| 假設 | 實測 | 結論 |
|---|---|---|
| embedding 不穩定 | 四次向量**位元完全相同** | ❌ |
| HNSW 近似搜尋 | 改 `strict_order` → 仍不一致 | ❌ |
| **ORDER BY 不是全序** | 補 `id` → **完全一致** | ✅ |

元凶是稀疏檢索：`ts_rank` 產生大量相同分數，
`LIMIT 200` 取哪 200 筆**在 SQL 語意上本來就未定義**。

後果比「排序稍微不同」嚴重得多：後段 chunk 一變，覆蓋率判定就翻面，
信心分數在 0.90 與 0.40 之間跳。50 題 A/B 比較中 6 題通過狀態改變
**全部源於此**，與當時被測的修正無關 —— **我們差點把雜訊當成效果**。
更嚴重的是稽核問「當初根據哪幾份文件」時，重跑會給出不同清單。

### 代價
理論上多一個排序鍵會慢一點。實測反而更快（2.35~3.99s vs 3.77~4.40s）。

### 重來一次還會這樣嗎？
**會，而且會更早做。** 教訓是：**任何 `ORDER BY` + `LIMIT` 的組合，
只要排序不是全序，回傳哪幾列就是未定義行為** —— 這不是效能細節，
是正確性問題。測試因此同時檢查「跑三次一樣」與「排序有沒有決勝鍵」，
少了後者，前者只是擲骰子。

## D-21 把驗證做成可執行的腳本，而不是紀律

**日期**：2026-08-12　**狀態**：✅ 維持

### 處境
同一個「回歸測試項數」在文件裡出現過 39、58、139、154 四個版本。
根因不是誰不小心，而是**同一個事實被抄寫在十幾個地方**。

### 決定
把「文件宣稱的數字」「答案卷的期待值」「技能檔的引用」
全部變成**可執行的檢查**，回傳非 0 就是失敗。

### 理由
在要交給評審、要說服金融機構的文件裡，
**數字對不上比數字不好看嚴重得多** —— 它會讓人合理懷疑其他所有數字。

這三道機制上線後立刻抓到真實錯誤：

| 機制 | 抓到什麼 |
|---|---|
| `validate_evalset.py` | **一部法規抓錯了檔案**（pcode 寫錯）、4 筆答案卷寫錯 |
| `check_docs_consistency.py` | 21 處過時數字 |
| `verify_skill.py` | 一列統計標錯基準 |

那部法規抓回來的是另一部法規 —— 檔名對、大小正常、狀態顯示成功、
**零錯誤訊息**。症狀只是「問那部法規永遠拒答」，
而我們一度把它歸咎於模型不夠好。

### 代價
三支腳本自己也出過錯（正則沒有邊界差點改壞正確文件、
替換位置偏移把 154 寫成 1549）。**驗證工具本身也需要被驗證。**

### 重來一次還會這樣嗎？
**會。** 但會在第一天就規定：
**新增語料來源必須宣告 `expect_contains`，抓完立刻驗內容。**
一份內容錯的文件，比缺少那份文件危險得多。

## D-22 儀表板是呈現層，不做任何運算

**日期**：2026-08-12　**狀態**：✅ 維持

### 決定
儀表板只取資料、排版、上色。所有數字來自既有模組，
測試強制驗證其原始碼不得出現 `def check_` 或 `def m_`。

### 理由
**同一個問題不能有兩個答案。** 若儀表板自己算一次集中度、
終端機算另一次，兩邊有一天會不一致，而使用者無從判斷該信哪個。

### 代價
儀表板無法做「只有畫面需要」的加工，要什麼就得回頭改後端模組 ——
這正是想要的：那些加工本來就該在能被測試的地方。

### 重來一次還會這樣嗎？
**會。** 但會更早把截圖納入版控 ——
把畫面截下來之後才發現四個 bug（完整性分數 67.4% 顯示成 0.7%、
文件筆數顯示 `[object Object]`、markdown 星號原樣印出、
現金流圖因量級差 50 倍而完全看不出變化）。
**那四個都已經在畫面上，沒有任何測試會抓，也沒有人會發現。**

---

## D-23 模擬重用既有算法，而非新造引擎

**日期**：2026-08-13　**狀態**：✅ 維持

### 決定
儀表板的情境模擬直接呼叫 `compute_cash_flow_projection()` ——
那支函式在資料產生器裡已存在，只是一直綁在命令列參數 `--stress` 上。

### 理由
**模擬與正式報告必須用同一套算法。**
若模擬另外寫一份，兩邊有一天會給出不同答案，而那時沒有人知道該信哪個。
這與 D-22 是同一條原則的不同面向。

### 代價
第一版只回報「第一個缺口」，導致加 3,000 萬與加 6,000 萬顯示完全相同 ——
因為基準線本來就有缺口且發生在更早。已改為比較**整段期間的最低餘額**。

### 重來一次還會這樣嗎？
**會。** 教訓是：比較兩個情境時，**要比的是對整體的影響，
而不是某個單點事件** —— 單點很容易被既有狀況蓋過而失去鑑別力。

## D-24 現金流不用雙 y 軸

**日期**：2026-08-13　**狀態**：✅ 維持

### 處境
餘額約 1,500 萬、單日入帳約 30 萬，量級差 50 倍。
畫在同一個座標軸上就是一條線貼頂、一排長條貼底，兩者都看不出變化。

### 決定
**上下兩張圖共用時間軸、各自尺度。** 不加第二個 y 軸。

### 理由
雙軸圖能解決視覺問題，但**它可以透過調整任一軸的範圍
製造出任意想要的相關性** —— 在金融場合尤其不該用。
一張可以被調成任何結論的圖，等於沒有資訊。

另兩個細節也寫下來：餘額圖**不從 0 起**（從 0 起會把 6% 的變化壓成平線），
長條圖**必須從 0 起**（長條的長度就是它編碼的量）。

### 重來一次還會這樣嗎？
**會。**

## D-25 儀表板改成案件佇列入口，且拿掉商業論證面板

**日期**：2026-08-20　**狀態**：✅ 維持

### 處境
第一版儀表板是「下拉選單挑一個委任案」——工程師測試單一租戶用的介面，
不是授信人員實際的工作模式。同一輪還一度把 KPI／市場規模／飛輪這些
給評審看的商業論證塞進了這個操作介面裡。

### 決定
**入口改成案件佇列**（依風險燈號與受理天數排序），點進去才是單一案件細節，
比照 Taulia／PrimeRevenue／Newgen 這類真實供應鏈金融平台的介面慣例。
**商業論證面板整個拿掉**——那組內容留在 `docs/BUSINESS_CASE.md` 才是對的地方。

### 理由
儀表板的使用者是銀行授信人員或中小企業，不是評審。
授信人員每天要用的操作介面裡出現「市場規模 SAM/SOM」，
只會讓人搞不清楚這是產品還是投資人簡報——這是使用者研究的基本錯誤，
不是「多加一個功能」，是放錯了對象。

### 代價
两邊各自需要維護：業務論證的實測數字（例如造假偵測 Recall/Precision）
現在同時活在 `docs/BUSINESS_CASE.md` 與 `docs/FRAUD_BENCHMARK.json`，
儀表板不再重複顯示，如果之後要在儀表板上展示同類數字，
必須確保是同一個資料來源，不能各自維護一份。

### 重來一次還會這樣嗎？
**會，但會更早問一句「這個畫面的使用者是誰」再動手，
不是做完才發現放錯地方。**

## D-26 VeriFin 全量重跑要能扛得住單份文件卡住

**日期**：2026-08-20　**狀態**：✅ 維持

### 處境
全量重跑要對 500+ 份文件各打一次 Ollama，跑好幾個小時。
`run_doc()` 原本沒有任何容錯，兩次真實發生問題：
一次是 `risk_coverage()` 在全數留白時漏回傳欄位，`render_report()`
存取時 `KeyError` 崩潰；一次是某份文件的請求卡住不動
（GPU 使用率同時掉到個位數，不是在算，是卡住），逼近逾時上限。
兩次都會讓前面已經跑完的幾百份文件全部作廢。

### 決定
`run_doc_safe()` 包一層容錯：逾時或任何例外都當成「這份文件抽取失敗」，
全部欄位計為留白（不是編一個答案），繼續下一份，並把單份逾時從
600s 收緊到 150s——短篇收據/表單實測每份 10~20s，卡到 150s 都拿不到
回應，代表這次請求本身有問題，繼續等不會讓它突然成功。

### 理由
**留白不是缺點，是誠實。** `strict_json_failure_rate` 本來就是要如實
反映 pipeline 真實中斷率的指標，一次逾時就該算進那個分母，
不能因為換了一種失敗方式（網路掛住而非模型答錯）就不計分。
一支跑幾小時、沒有任何容錯的批次腳本，本質上是拿一整晚的算力去賭
**沒有任何一份文件會出狀況**——這個賭注沒有必要冒。

### 重來一次還會這樣嗎？
**會，但長時間批次腳本從第一版就該假設「某一筆會出問題」，
不是出事之後才補。**

## D-27 自動化比例從「實測」降級為「推算」（已推翻）

**日期**：2026-08-20　**狀態**：❌ **已推翻**（本專案第四次被自己的驗證機制推翻的決定——
前三次分別是模型選型、技能檔統計、法規語料，見 `HANDOVER.md` §6）

### 處境
`scripts/roi_model.py` 的「可自動化比例」曾經是 ROI 模型裡**唯一標成「★實際量測」
而非假設**的參數，值為 0.60，來源是 VeriFin 的 Risk-Coverage 曲線
（「在錯誤率壓到 5% 以下的前提下，系統能自動處理的欄位比例」），
但那個量測只跑了 **12 份文件**的小樣本。

### 決定
2026-08-20 VeriFin 全量重跑（SROIE 361 份文件）後，這個量測結果是：
**AURC 0.34、coverage_at_target_risk 只有 0.14%**——風險曲線幾乎打平，
不管挑信心分數前 1% 還是前 99% 的預測，錯誤率都在 33~35% 之間浮動。
**模型自報的信心分數，在全量下幾乎不能預測答案對不對。**

把「可自動化比例」的依據等級從「★ 實際量測」**降為「⚠️ 推算」**，
數值暫時保留 0.60（避免無憑無據另編一個數字），
但明確標示這個數字目前**沒有有效的量測方法支撐**。

### 理由
**這不是系統不準**——SROIE 整體準確率仍有 65.2%，模型本身的抽取能力沒有崩壞。
崩壞的是「用模型自己講的信心分數，去決定要不要跳過人工複核」這個機制本身——
12 份文件的小樣本剛好呈現出一條看似有鑑別力的曲線，
361 份文件的全量測試證明那是抽樣噪音，不是真訊號。

**這件事反而印證了本產品最核心的架構主張**：`crosscheck.py` 從一開始就
設計成零 LLM、決定性規則，不信任模型自報的信心去做風險判斷——
如果我們真的做了一套「LLM 信心 > 門檻就自動放行」的系統，這次全量重跑
測到的 0.14% 就是那套系統在真實世界會發生的事。

### 代價
BUSINESS_CASE.md／PROPOSAL_SUBMISSION.md 的 KPI 表格裡「憑證人工檢查比例
40%（其餘 60% 系統自動比對通過）」這一列，連帶失去「★實測」的立足點，
一併改標為待驗證。三個 ROI 情境（保守/基準/樂觀，年化效益 108.8萬/331.2萬/
678.0萬）用的 automation_ratio（0.40/0.60/0.75）現在也全部是**未驗證的假設值**，
不是量測值——簡報與提案書裡若引用這幾個數字，必須拿掉「實測」字樣。

### 重來一次還會這樣嗎？
**會，而且會更早用全量資料測，不要讓一個 12 份文件的小樣本
撐起「這是本模型唯一的實測參數」這麼重的宣稱。**
樣本數不夠大時，「量測出來的數字」跟「隨機噪音」在統計上經常無法區分——
這正是 `docs/BUSINESS_CASE.md` 已經記錄過的另一次教訓（D-15，覆蓋率門檻
最初也是拿 8 題探測樣本訂的）。同一類錯誤，這是第二次用不同參數重演。

## D-28 決定性路由要判斷「問誰」，不只「問什麼」

**日期**：2026-08-20　**狀態**：✅ 維持

### 處境
105 題全量評測抓到一個真的會端出錯答案的路由 bug：
「信保基金去年的呆帳率是多少？」被關鍵詞「呆帳」路由到 `ageing`——
但那個指標算的是**本案自己**帳上的帳齡與呆帳沖銷比率（0.52%），
不是信保基金這個機構自己的統計。系統把本案自家數字當成信保基金的
統計數字端出來，信心還打了 1.00——因為決定性路徑不經過
`evidence.py` 的信心與拒答閘門，原本沒有任何東西能攔下「問錯對象」。

### 決定
`metrics.route()` 在比對關鍵詞之前，先檢查問題裡有沒有出現具名的
第三方機構（沿用 `graph.PUBLISHER_JURISDICTION`，同一份名單不重複維護，
另加「信保基金」「玉山銀行」等口語簡稱）。一旦問題點名了外部機構，
就跳過所有「算本案自己帳上數字」的路由（concentration/ageing/
cashflow/summary），讓問題落到 RAG——寧可拒答，也不要套錯分母
還打滿分信心。

### 理由
這是 U-01（「日本的保證成數」與「台灣的保證成數」在語意上重合）的
同一類問題，只是這次發生在**決定性路徑**而不是 RAG 路徑。
`evidence.py` 已經有一套範圍詞驗證機制處理 RAG 那一側，
但決定性路徑完全獨立於那套機制之外——**這是一個沒人想到要問的問題：
「零 LLM、決定性運算」是不是也需要範圍驗證？答案是需要，
決定性不等於問對了問題。**

### 代價
修法刻意保守：只要問題提到具名機構，就完全跳過本案的決定性計算，
即使那個問題其實是在問「本案跟那家銀行往來的逾期狀況」這種
合法的本案問題。這會把一些合法問題也推去 RAG，但代價遠低於
「決定性路徑打著 100% 信心端出錯答案」。

### 重來一次還會這樣嗎？
**會，而且會在設計任何『零 LLM 保證正確』的路徑時，
先問一句：這條路徑要怎麼知道問題問的是誰。**
「決定性」保證的是算術正確，不保證問題理解正確——
兩者是不同層次的正確性，混為一談就是這次 bug 的根源。

### 驗證
修完不能假設會更好，必須重跑 105 題全量才算數：
拒答正確率 85.0% → **90.0%**（20 題應拒答中，產生幻覺的題數從
3 題降到 2 題），整體通過率 77.1% → 78.1%。改善幅度不大，
是因為這個 bug 本來就只影響「問第三方機構自己的數字」這一小類問題，
但**方向正確且可重現**，比改善幅度更重要。

# 未來方向：目前架構解決不了的問題

> 這一節不是 roadmap（那是排程），是**已知的原理性限制**。
> 寫出來是為了讓接手的人不要重複踩，也讓評審知道我們清楚邊界在哪。

## U-01 主題相似但指涉對象不存在

**問題**：「日本的保證成數」與「台灣的保證成數」在語意空間裡幾乎重合。
向量相似度在**原理上**就不處理「指涉對象是誰」。

**目前的緩解**：範圍詞驗證（D-16），精確但不完整（3/8）。

**真正的解法方向**（需驗證，非既定結論）：
1. **結構化實體比對** —— 把每份文件的「適用範圍」抽成結構化欄位
   （國家、年度、法規版本、適用主體），檢索時比對問題與文件的範圍欄位。
   這需要知識圖譜或至少是 metadata schema，不是靠相似度。
2. **檢索不到就明確說明並提供替代** —— 而不是給一個看起來相關的答案。
   目前拒答訊息已朝這個方向，但還可以更具體：
   「本知識庫不含日本制度。可提供台灣的對應規定供參考，
   但**這不是您問的數字**，來源為 XXX。」
3. **外部檢索的 tool use** —— 知識庫撈不到時能上網查證。
   但這會引入新的可信度問題（網路來源的權威性），
   且小模型的 tool use 可靠度不足，需要謹慎設計。

## U-02 全套自洽的偽造憑證

跨文件比對抓的是「憑證之間的矛盾」。
一套精心偽造、彼此完全自洽的憑證，這個方法**抓不到**。
需要物流單、報關單等外部佐證，或與買方系統直接對接。

**這一點必須在對外說明能力邊界時明講，不能含糊。**

## U-03 LLM 校準

模型自報信心與實際正確率脫節，是學界未解問題。
本系統的做法是**繞過** —— 信心由外部可量測訊號算出，不採信模型自報。
但這也意味著我們無法利用模型自身的不確定性資訊。
